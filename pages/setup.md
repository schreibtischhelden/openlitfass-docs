# Setup

An openLitfass calendar is an **instance**: a directory with configuration,
sources and styling. The code comes from the container image
`ghcr.io/schreibtischhelden/openlitfass`. Setting up a calendar therefore
means creating an instance directory and choosing where the image runs
against it.

| Way to run | Good for | Needs |
|---|---|---|
| [GitHub Actions and GitHub Pages](#run-with-github-actions) | most instances; no server of your own, data history in Git | a GitHub repository |
| [Self-contained container](#run-as-a-container) | your own server, a NAS, a Raspberry Pi | Docker or Podman |
| [Docker Compose](#docker-compose) | the container next to a reverse proxy | Docker Compose |

Both ways use the same instance directory, so you can switch later.

## Create an instance

> **Tip:** the [config UI](https://config.openlitfass.org) builds
> `instance.json`, `categories.json`, `places.json`, inbox events and source
> files with forms in the browser. Nothing is sent to a server; you download
> the file and put it into the instance directory.

1. Create a new, empty repository (or directory) for your calendar.
2. Copy the content of
   [`example-instance/`](https://github.com/schreibtischhelden/openlitfass/tree/main/example-instance)
   from the core repository into it.
3. Edit `instance.json`: at least `name`, `title`, `baseUrl` and `timezone`,
   by hand or with the [config UI](https://config.openlitfass.org/?page=instance).
   All fields: [instance.json](?page=configuration#instancejson).
4. Adapt the legal notice (`site/impressum.html`) and the privacy policy
   (`site/datenschutz.html`), or point `imprintUrl` and `privacyUrl` to
   existing pages. A public website operated in Germany needs a legal notice.
5. Add sources: copy a template from `sources/`, remove `.example` from the
   file name and adjust the URL and mapping, or create the file with the
   [source wizard](https://config.openlitfass.org/?page=source). See
   [Sources](?page=sources) and [Finding sources](?page=source-discovery).
6. Optional: colours and logo in `site/` ([Theming](?page=theming)), venues in
   `places.json` ([Places](?page=places)), holidays in `holidays.json`
   ([Event inbox](?page=inbox#day-lists-holidaysjson)).

The result looks like this:

```
my-calendar/
  instance.json            required: name, title, time zone, …
  categories.json          categories and icons (order = menu order)
  places.json              optional: venues, parks, sights
  holidays.json            optional: named day lists for recurring events
  sources/*.json           one file per source (*.example.json = template)
  inbox/*.json             single events added by hand
  site/                    styling: css/theme.css, logo.svg, legal pages, …
  data/                    generated by fetch; commit it
  public/                  generated by build-site; do not commit
  .github/workflows/update-events.yml
```

Details of every file: [Configuration reference](?page=configuration).

### Try it locally

With Docker you can look at the instance before publishing it:

```sh
docker run --rm -v "$PWD:/instance" -p 8080:8080 ghcr.io/schreibtischhelden/openlitfass:0.4
```

Open <http://localhost:8080>. The container fetches all sources once, builds
the site and serves it. Add `-e OL_FETCH_INTERVAL=0` to only serve what is
already in `data/` without fetching.

> **Note:** on Windows with Git Bash, write the mount as
> `MSYS_NO_PATHCONV=1 docker run … -v "$(pwd -W):/instance" …` so the path
> survives.

## Run with GitHub Actions

The example instance contains the workflow
`.github/workflows/update-events.yml`. It runs every six hours, by hand, and
on every push that changes content (`instance.json`, `categories.json`,
`holidays.json`, `sources/`, `inbox/`, `site/`). Each run:

1. starts the image with `docker run` and runs `fetch`: new
   `data/events.json`, `categories.json` and `sources.json`, the `status` of
   every source, and deletion of expired inbox files;
2. runs `build-site`, which writes the finished site to `public/`;
3. commits `data/`, `sources/` and `inbox/` back to the repository.

Steps:

1. Set `IMAGE` in `update-events.yml` to the image tag you want, for example
   `ghcr.io/schreibtischhelden/openlitfass:0.4` (see
   [Updating](?page=updating#choosing-an-image-tag)).
2. Push the repository to GitHub.
3. Run the workflow once by hand (*Actions → Update events → Run workflow*)
   and check the result in `data/events.json`.

The template does not publish `public/` anywhere. To publish to GitHub
Pages, add the step described in
[Publishing on GitHub Pages](?page=github-pages).

The workflow starts the image with `docker run` on an Ubuntu runner instead
of using it as a job container, because GitHub's JavaScript actions do not
run in Alpine containers. The same workflow works on Forgejo or Gitea runners
that provide Docker.

## Run as a container

The image's default command is `serve /instance`. Mount the instance
directory and publish port 8080:

```sh
docker run -d --name my-calendar --restart unless-stopped \
  -v /srv/my-calendar:/instance \
  -p 8080:8080 \
  ghcr.io/schreibtischhelden/openlitfass:0.4
```

`serve`:

- serves the site on port 8080 from the existing data within seconds of
  starting;
- fetches all sources immediately and then every `OL_FETCH_INTERVAL`
  (default `6h`), and rebuilds the site. Each build goes into a new
  directory and goes live only once it is complete, so a failed build leaves
  the previous version online;
- writes to the instance directory like `fetch` does: `data/`, the `status`
  field of each source, deletion of expired inbox files;
- reports its state at `/healthz` and metrics at `/metrics`
  ([Monitoring](?page=monitoring)).

All settings are environment variables starting with `OL_`:
[Environment variables](?page=configuration#environment-variables).

### File permissions

The image runs as the unprivileged user `65532:65532`. `serve` writes to the
mounted directory (`data/`, `sources/`, `inbox/`, `.openlitfass-serve/`), so
that user needs write access. Either start the container as the owner of the
directory:

```sh
docker run -d … --user "$(id -u):$(id -g)" -v /srv/my-calendar:/instance ghcr.io/schreibtischhelden/openlitfass:0.4
```

or give the directory to the image's user once:

```sh
sudo chown -R 65532:65532 /srv/my-calendar
```

On Docker Desktop (Windows, macOS) mounted directories are writable either
way. The `update-events.yml` workflow already passes `--user`.

### HTTPS and a custom domain

`serve` speaks plain HTTP. Put a reverse proxy in front of it for HTTPS
(Caddy, Traefik, nginx). `serve` sets suitable cache headers itself: HTML
pages, data and the service worker are revalidated on every request.

With Caddy, for example:

```
calendar.example.org {
	reverse_proxy localhost:8080
}
```

### Keeping the data in Git as well

If you want the history of `data/` in your repository, use the GitHub
Actions workflow for fetching (or in addition) and start the container with
`OL_FETCH_INTERVAL=0`: it then only serves what the workflow committed, after
a `git pull` on the server.

## Docker Compose

```yaml
services:
  calendar:
    image: ghcr.io/schreibtischhelden/openlitfass:0.4
    restart: unless-stopped
    user: "1000:1000"            # owner of ./my-calendar
    volumes:
      - ./my-calendar:/instance
    ports:
      - "127.0.0.1:8080:8080"    # only for the reverse proxy on this host
      - "127.0.0.1:9090:9090"    # metrics, not public
    environment:
      OL_FETCH_INTERVAL: 6h
      OL_METRICS_ADDR: ":9090"
      OL_STATIC_PAGES: "true"
      OL_SITEMAP_GENERATOR: "true"
```

The image has a built-in `HEALTHCHECK` against `/healthz`, so
`docker compose ps` shows whether the instance is healthy.
